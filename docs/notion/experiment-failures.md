# 실험이 잘되지 않는 원인 찾기

[연구 가이드 목록](./README.md) · [한국어판 처음으로](../../README.md)

원문: [공개 Notion](https://pengsida.notion.site/1aee6e718de6472f834d13da8f4ff097) · [Sida Peng의 Learning Research](https://github.com/pengsida/learning_research)

원문 확인일: 2026년 11월 4일.

원인을 알아야 방법을 효과적으로 개선할 수 있습니다. 이 문서의 목적은 새로운 아이디어 자체를 만드는 것이 아니라 **현재 실험이 실패하는 이유를 찾는 것**입니다.

원저자는 [William T. Freeman의 연구 안내](http://people.csail.mit.edu/billf/www/papers/doresearch.pdf)를 주요 참고 자료로 소개합니다. 실험 결과를 분석하지 않으면 프로젝트가 늦어지거나 실패하고, 다른 연구가 먼저 발표되어 투입한 시간이 성과로 이어지지 않을 수 있다고 경고합니다.

## 1. 실패 사례 모으기

성능이 나쁜 결과와 눈에 보이는 이상 현상을 모읍니다. 막연히 ‘안 된다’고 표현하지 말고 어떤 데이터와 조건에서 어떻게 실패하는지 기록합니다.

## 2. 성공 사례나 작동하는 버전 찾기

성능이 좋은 사례를 모으거나, 실험을 단순화해 작동하는 버전을 찾습니다.

| 단순화할 대상 | 원문의 예시 |
| --- | --- |
| 데이터의 복잡도 | 큰 장면을 작은 장면으로, 복잡한 조명을 단순한 조명으로, 복잡한 재질을 단순한 재질로 변경 |
| 과제 조건 | 일반화 대신 주어진 데이터에 대한 적합, 희소 시점 대신 조밀한 시점, RGB 감독 대신 RGB-D 감독, 데이터 수 감소 |
| 제안한 개선 요소 | 자신이 추가한 알고리즘 요소를 하나씩 제거 |

## 3. 성공과 실패 사이의 차이 분석하기

### 작동하는 버전과 작동하지 않는 버전이 있을 때

작동하는 버전에서 시작해 과제를 조금씩 어렵게 만들거나 개선 요소를 하나씩 추가합니다. **한 번에 한 요소만 바꾸어**, 어느 변화가 실패를 일으키는지 찾습니다. 원인을 가능한 한 단일 요인으로 좁히는 것이 좋습니다.

그 요인을 찾았다면 기술적 원인 후보를 최대한 많이 적고 우선순위를 매깁니다.

### 같은 방법에서 성공 사례와 실패 사례가 나뉠 때

두 집단의 데이터를 비교해 어떤 특성 차이가 성능 차이로 이어지는지 살펴봅니다. 그다음 데이터 차이를 설명할 수 있는 기술적 원인을 여러 개 제시하고 우선순위를 매깁니다.

### 공통으로 살필 원인

- **구현 오류:** 줄별 출력, 텐서의 형태, 시각화 결과가 예상과 맞는지 확인합니다. 알고리즘을 잘못 이해한 문제라면 논문과 원리를 다시 읽은 뒤 코드를 점검합니다. [디버깅 가이드](./debugging-guide.md)를 참고합니다.
- **하이퍼파라미터:** 설정이 현재 데이터와 조건에 맞는지 확인합니다.
- **빠진 구현 요소:** 관련 논문이 효과를 얻는 데 필요한 기법을 사용하고 있는지 확인합니다. 원문은 NeRF의 위치 인코딩을 예로 듭니다.
- **데이터의 적합성과 난도:** 데이터가 방법에 맞는지, 너무 어려운 것은 아닌지 살펴봅니다. 더 단순한 데이터와 비교할 수 있습니다.
- **알고리즘 자체의 한계:** 해당 조건에서 방법의 가정이나 구조가 성립하는지 확인합니다.

관련 논문은 같은 모듈이나 통찰을 쓰는 연구, 비슷한 기술적 난점을 해결하는 연구까지 넓혀 찾습니다. 원저자는 이 단계에 모든 상황을 해결하는 보편적인 분석법이 있는 것은 아니며, 지도교수와 동료와의 토론을 적극 권한다고 덧붙입니다.

## 4. 원인 후보를 실험으로 검증하기

가설은 결국 실험으로 확인해야 합니다. 원문은 양즈린의 경험담을 인용해 많은 실패를 기록하면서 빠르게 반복하는 태도를 소개합니다. 성공 결과가 나오기까지 기록한 실험 수가 매우 많았다는 개인 경험이며, 보편적인 성공 확률이나 필요한 실험 횟수로 받아들이지는 않습니다.

**빠른 반복은 유효한 실험을 전제로 합니다.** 아무 가설 없이 무작정 실험을 늘리면 오히려 상황이 복잡해질 수 있습니다. 무엇을 확인하려는 실험인지, 결과가 어떤 가설을 지지하거나 배제하는지 분명히 하세요. 원문에 인용된 ‘불가능한 가능성을 제거해 원인을 좁힌다’는 문구도 이러한 맥락입니다.

## 5. 확인된 원인에 맞는 해결책 만들기

기술적 원인을 확인한 뒤 해결책을 제안합니다. [문헌 지도](./literature-tree.md)를 만들어 사용할 수 있는 기술을 축적해 두면 도움이 됩니다.

현재 접근이 올바른지 주기적으로 돌아보고, 좁은 생각에 갇히지 않도록 동료들과 논의하세요.

## 첨부 흐름도 읽기

첫 흐름도는 아이디어 → 실험 → 실패 → 분석 없이 아이디어 변경 → 재실험의 반복을 보여 줍니다. 원문은 이를 잘못되거나 무작위인 기울기에 비유합니다. 성공했을 때는 다음 실험으로 넘어갑니다.

두 번째 흐름도는 실패를 분석하는 경로를 나눕니다.

| 상황 | 다음 단계 |
| --- | --- |
| 같은 실험에 성공·실패 데이터가 모두 있음 | 데이터의 차이를 비교해 겉으로 드러나는 원인을 찾음 |
| 모든 데이터에서 실패하지만 작동할 것으로 예상되는 다른 알고리즘이 있음 | 그 알고리즘을 실행하고 방법 사이의 차이를 비교 |
| 작동할 방법이 떠오르지 않음 | 더 단순한 데이터로 바꾸고 재실험 |
| 단순한 데이터에서는 성공함 | 원래 데이터와 비교하여 차이를 찾음 |
| 단순한 데이터에서도 실패함 | 가능한 알고리즘과 데이터 조건을 다시 검토 |

이후 구현 버그인지 알고리즘의 실제 한계인지 기술적 원인을 분석합니다. “작동할 알고리즘”은 이미 실행해 본 방법만 뜻하지 않고 경험상 가능성이 있는 방법도 포함합니다.

외부 조언 이미지들은 실패를 보고하는 데서 멈추지 않고 대안을 탐색하기, 어느 단계까지 정상인지 설명하기, 가정을 확인하며 한 번에 하나씩 바꾸기를 강조합니다. 해당 인용은 요약으로 제공하며 Freeman과 양즈린의 첨부 PDF 전문은 번역·재배포하지 않습니다.
